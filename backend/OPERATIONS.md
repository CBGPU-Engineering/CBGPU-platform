# Live CBGPU services

The active checkout is `/home/cbgpu/CBGPU-live`. The frontend binds to loopback port 3000, developer/admin gateway port 3400, local backend port 54321 and public notebook gateway port 3500. Cloudflare Tunnel publishes HTTPS; these loopback services do not require inbound router ports.

- `cbgpu.com`: main website and local-backend reverse proxy.
- `developers.cbgpu.com`: two named developer accounts, real CBGPU account password followed by the separate system password. Host-only Secure/HttpOnly cookies, CSRF, login throttling and eight-hour sessions. Account/admin revocation closes access.
- `admin.cbgpu.com`: the same two-stage gate, then the main application's admin interface. The user site exposes no administrative navigation or management controls, including for administrator accounts. User-host `/admin` paths and management API paths return404. Access this host directly. Native account tokens stay encrypted on the server until the authenticated browser restores its own account session.
- `docs.cbgpu.com`: public guides.
- `arxiv.cbgpu.com`: public school preprints. Normal CBGPU accounts can publish PDF manuscripts; uploads have per-user limits, private storage and server-mediated downloads. Publication makes the manuscript public. No peer-review claim is implied.
- `gpu.cbgpu.com/1/` through `/4/`: password-protected Jupyter notebooks. The gateway starts a second base-path-aware notebook process inside each existing container, preserving existing kernels and files. It reconciles after normal controller container resets. Reservation passwords are available only to the active approved reservation holder or server administrators.

## Backups and monitoring

`cbgpu-backend-backup.timer` creates a daily database/storage/configuration snapshot, then encrypts and uploads it to a private Cloudflare Worker/KV store. AES-256-GCM encrypts the complete archive before upload; chunk and archive SHA-256 checks detect corruption. The newest three snapshots are retained, with an eight-day expiry for orphaned chunks. Archives have a 160 MiB safety ceiling to keep the configured storage within its free-tier limit.

Backups include database roles, Auth records, uploaded storage, Vault encryption keys, consistent developer SQLite/configuration, source code, service files, GPU-controller configuration and Android signing material. Installed dependencies, build caches, APK binaries and GPU training datasets/container layers are excluded. Reinstall dependencies and rebuild the frontend/app during disaster recovery. Shared-material files are included in materials.tar.gz; their service uses the public same-origin /api/files gateway with authenticated8MiB resumable chunks. The Android1.0.4 bridge uses the same public endpoint and loads app.cbgpu.com. GPU workloads need separate dataset/container backups if they must survive loss of this computer.

The private recovery kit is available from the developer Account & security page after a recent login. A private copy also lives in the owner's Google Drive CBGPU recovery folder; it contains both the storage access credential and decryption key. Protect it like a server credential. The Worker contains encrypted archives, while Google Drive holds the recovery material separately.

`cbgpu-backend-restore.timer` downloads and verifies the newest backup weekly, restores it into a network-isolated PostgreSQL 17 container, compares source counts and verifies Vault decryption. It never replaces the live database. `node backend/operations/verify-latest.mjs` runs the same check manually.

A Cloudflare Worker probes the website, developer/admin portals, docs, preprints, all four GPU login pages, local backend readiness and offsite-backup freshness every minute. Three failures trigger an email to both developers; two successes trigger recovery mail. Monitoring continues if this PC goes offline. Provider email quotas still apply. The portal's operations page shows backup and external-monitor status.

## Compose readiness failure diagnostics

Compose starts with --wait --wait-timeout300. A nonzero exit or deployment timeout remains an error. Before returning failure, the worker captures project-scoped `docker compose ps -a`, timestamped service logs (tail200), container state/exit/OOM metadata and `.State.Health.Log` for unhealthy, starting or failed containers. Known environment credentials and JWTs are redacted. Output is bounded and persisted in both deployment SQLite logs/diagnostics and the release's private failure-diagnostics.json.

The supervisor preserves failed containers and volumes and does not automatically run down or roll back an earlier configuration on failure. This retains the failing configuration for diagnosis. Stop/delete remains an explicit action. Failed readiness clears the previous deployed timestamp. The existing Compose error panel opens the diagnostic log automatically, and its error message lists failed services. Per-release diagnostic snapshots survive subsequent deployment log resets. `capture-compose-failure.py PROJECT_UUID` can collect read-only diagnostics for an existing failed deployment; it never starts or stops containers. Tests: verify-compose-failure.py (real unhealthy container, redaction, container/data preservation), verify-compose-manager-failure.mjs (persistent error state, no cleanup/rollback, previous success timestamp cleared), verify-compose.py (healthy deployments and data-preserving redeploy).
