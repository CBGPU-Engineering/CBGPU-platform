# CPU 공개 서버 주소 미설정 (2026-10-26)

## 원인

- 기존 웹은 Public 프로젝트의 접속 주소를 `NEXT_PUBLIC_CPU_SERVER_PUBLIC_HOST`에서 만들었다. 운영 배포 환경에 이 값이 없어 상세 화면에 `공개 서버 주소 미설정`이 표시됐다.
- 운영 데몬은 Public 컨테이너를 `0.0.0.0:<포트>`에 게시했지만, 외부에서 사용할 안정적인 HTTPS 주소를 발급하거나 DB에 기록하지 않았다.
- 앱은 실제 주소 대신 `http://[서버IP]:<포트>`를 표시했다.

## 변경

- Public 프로젝트마다 Cloudflare 임시 터널을 만들어 `cpu_projects.public_url`에 HTTPS 주소를 기록하고, 웹과 앱이 이 값을 표시한다.
- 새 Public 배포는 루프백·교내 주소·Tailscale 주소에만 바인딩한다. 터널은 루프백으로 연결한다. 기존 컨테이너의 바인딩은 안전한 재배포 전까지 그대로다.
- 터널의 생성과 재시작 후 주소 갱신은 CPU 작업자에서 처리해 GPU 예약 확인을 막지 않는다. 삭제 시 터널과 기존 UFW 공개 규칙을 제거한다.
- 통제된 데몬 롤아웃 중에는 `/run/cbgpu-daemon-preserve-idle-once` 표식으로 유휴 GPU 컨테이너의 시작 시 초기화를 한 번 건너뛸 수 있다. 표식은 검증 후 제거한다.

## 검증과 운영 상태

- Supabase 운영 DB에 `public_url` 컬럼이 있음을 읽기 전용으로 확인했다.
- 독립적인 nginx 시험 컨테이너와 cloudflared 터널로 루프백 HTTP 200, 임시 HTTPS HTTP 200을 확인했다. 시험 컨테이너를 모두 삭제했다.
- 데몬 단위 테스트 24개와 웹 TypeScript 검사 통과. Flutter/Dart 도구는 이 환경에 없어 정적 검사는 실행하지 못했다.
- 운영 데몬에 SHA-256 `0c2574f44fa9b5734e6c97f6072ce8c95b04d3b1a87a3c0a749f2c8bb27b6f4b` 수정본을 반영했다. 네 GPU 컨테이너의 ID와 실행 상태는 반영 전후 같았고 일회성 보존 표식은 제거됐다.
- 기존 `ai-top100-bot`의 `public_url`이 자동 기록됐으며, 해당 Cloudflare HTTPS 주소가 HTTP 200을 반환했다. 기존 앱 컨테이너는 재생성하지 않았다.
- 별도 임시 Public nginx 프로젝트를 `pending`으로 만들고 `approved`로 변경했다. 데몬이 자동 배포하고 `public_url`을 기록했으며 HTTPS 200(896바이트)을 확인했다. 호스트 바인딩은 `127.0.0.1`, `10.138.23.12`, `100.100.136.37`에만 있었다. `deleted`로 변경한 뒤 데몬이 앱과 터널 컨테이너를 제거했고 시험 DB 행도 정리했다.
- 웹·앱의 주소 표시 수정은 이 문서 작성 시점에 배포 여부가 확인되지 않았다. 운영 웹은 해당 프런트엔드 배포 전까지 종전 문구를 보여줄 수 있다.

## 주의

- `*.trycloudflare.com` 임시 주소는 터널 재시작 시 바뀔 수 있다. 고정 주소가 필요한 프로젝트에는 관리형 터널과 도메인이 필요하다.
- 이미 `0.0.0.0`에 게시된 프로젝트는 터널 주소가 생겨도 직접 포트가 닫히지 않는다. 서비스 중단을 허용할 수 있는 때에 재배포하고 바인딩을 확인해야 한다.
