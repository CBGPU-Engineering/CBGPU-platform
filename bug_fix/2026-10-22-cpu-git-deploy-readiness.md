# CPU Git 프로젝트 승인 후 배포 실패 (2026-10-22)

## 확인한 현상

- 승인된 공개 CPU 프로젝트가 배포되지 않았다. 처음에는 서버 UFW가 실제로 비활성 상태여서 데몬의 공개 포트 안전 검사를 통과하지 못했다.
- UFW를 활성화한 뒤에는 Python 프로젝트의 `pyproject.toml` 의존성이 설치되지 않아 `ModuleNotFoundError: No module named 'dotenv'`로 종료됐다. 데몬이 최상위 `requirements.txt`만 설치한 것이 원인이다.
- 의존성을 설치해 재시도하자 프로젝트 실행 명령의 `--host`, `--public-port`가 앱에서 지원되지 않아 종료됐다. 앱 소스는 `127.0.0.1`에만 바인딩하며, 인증 없는 로컬 전용 시제품이라고 명시한다. 따라서 공개 주소에 바인딩하도록 임의 수정해서는 안 된다.
- 설치 완료 마커가 실행 명령보다 먼저 생성되므로, 기존 데몬은 앱이 곧바로 종료되더라도 배포 완료 시각을 기록할 수 있었다.

## 조치와 현재 상태

- 기존 접속 경로를 확인하고 UFW를 활성화했다. SSH, 교내 SSH 게이트웨이, Tailscale 게이트웨이, GPU Jupyter의 TCP 연결을 확인했고 자동 되돌리기 타이머를 중지했다.
- 별도 앱인 BACKSPACE는 자체 실행 인자 오류로 종료된다. 이 앱의 코드를 플랫폼에서 수정하지 않았다. 해당 앱의 정상 HTTP 응답은 확인되지 않았다.
- 데몬은 `requirements.txt`가 없는 Python Git 프로젝트에서 `pyproject.toml`을 설치하고, 설치 완료 마커를 본 뒤에도 3초간 컨테이너가 유지되는지 확인하도록 수정해 운영 서버에 반영했다. 반영 전후 GPU 컨테이너 4대의 ID와 실행 상태가 같았다.
- 별도 임시 비공개 Docker 프로젝트를 신청·승인했을 때 데몬이 자동 배포했고 HTTP 200과 DB 배포 완료 시각을 확인했다. 테스트 컨테이너와 DB 행은 정리했다.
- 독립적인 PyPA Python 예제는 Git 복제 후 의존성 설치가 180초를 넘어 기존 시작 제한에 걸렸다. 이 동안 CPU 배포가 GPU 예약 폴링과 같은 루프를 막았다. 이 추가 문제에 대해 Git 설치 제한을 600초로 늘리고 CPU 작업을 최대 2건의 별도 작업으로 실행하도록 수정했다. 실패한 프로젝트는 같은 배포 요청에 대해 5분간 재시도를 늦춘다.
- 두 번째 수정본을 운영 데몬에 반영했다(파일 SHA-256 `b4d2de362c6079b22a484508d95798d6dde1f74659ca260fdb0094a8ad01870d`). 반영 전후 GPU 컨테이너 4대의 ID와 실행 상태가 같았다.
- 임시 비공개 Python Git 프로젝트를 `pending`으로 생성한 뒤 `approved`로 변경했다. 데몬이 44초 만에 배포해 DB `deployed_at`을 기록했고 HTTP 200(603바이트)을 반환했다. `deleted`로 바꾼 뒤 데몬의 컨테이너 삭제 로그를 확인했고, 임시 볼륨과 DB 행도 정리했다.

## 범위와 남은 작업

- 승인된 유효한 Python Git 프로젝트의 자동 배포와 삭제는 운영에서 확인했다. 모든 외부 앱의 실행 명령과 서비스 응답을 보장하는 검증은 아니다.
- BACKSPACE 소유자는 앱의 지원 인자, 외부 접속 바인딩, 인증 정책을 별도로 수정해야 한다. 플랫폼은 그 앱에 특화된 코드를 넣지 않는다.
- 로컬 Git 커밋과 운영 서버 코드가 일치하도록 저장소 반영이 필요하다. 프런트엔드 메모리 표시 변경은 Vercel 배포가 별도로 필요하다.
