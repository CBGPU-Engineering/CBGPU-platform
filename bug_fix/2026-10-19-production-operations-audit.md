## 발견 사항과 나중에 함께 수정할 작업

### 1. 운영 데몬은 최신 안전 조치가 적용되지 않았다 — 높음

운영 `/home/cbgpu/CBGPU/Daemon/daemon.py` SHA-256은 `5b7d8a96...`, 현재 저장소 `Daemon/daemon.py`는 `3a74a19b...`다. 운영 파일의 GPU reset 경로는 기존 컨테이너에 `docker rm -f`를 실행한 뒤 `docker run`을 한다. 저장소에는 먼저 새 컨테이너를 준비하고 실패 시 되돌리는 로직이 있다. 운영 파일에는 CPU 프로젝트 이름 접두어 충돌 검사와 교내 NIC 바인딩도 없다. 데몬 프로세스 자체도 최신 커밋 이전에 시작했다.

**수정 묶음:** GPU/CPU 작업이 없는 시점을 확인하고 Docker 교체 실패 복구를 별도 시험한 뒤, 데몬 코드·설정을 배포하고 서비스를 재시작한다. 재시작 전후 예약, GPU 파일, SSH, Jupyter 연결을 점검한다. `Migrations/guard_cpu_project_container_names.sql`은 현황 조회 후 적용한다. SQL 인덱스의 현재 운영 적용 여부는 이번 REST 검사만으로 확인되지 않았다.

### 2. 자료 공유 운영 이미지도 동시 업로드 수정 전 버전이다 — 중간

컨테이너의 `/app/app.py` SHA-256은 `676b0242...`, 저장소 `MaterialShare/app.py`는 `abf5183d...`다. 운영 이미지의 `_inflight[material_id]` 대입 직전에는 같은 ID가 이미 진행 중인지 확인하는 분기가 없다. Docker healthcheck도 없고 `/health`는 저장소·DB 상태와 무관하게 고정 `ok`를 반환한다. 지금 저장된 파일과 메타데이터는 0건이므로 현재 저장량은 작지만, 업로드 가능한 상태를 health 응답만으로 보장할 수 없다.

**수정 묶음:** 현재 이미지와 `service.env`를 보존한 뒤 이미지를 빌드·교체한다. 인증된 업로드·다운로드·삭제와 중복 업로드 409 동작을 검증한다. DB 인증과 디스크 상태를 확인하는 readiness endpoint 및 Docker healthcheck를 추가한다. 서비스 여러 프로세스에서의 총 용량 동시성은 별도 설계가 필요하다.

### 3. GPU Jupyter 포트가 모든 호스트 주소에 게시돼 있다 — 높음, 실제 외부 노출 범위 미확정

네 GPU의 컨테이너 포트 8888이 호스트 `0.0.0.0:8001`~`8004`와 `[::]:8001`~`8004`로 게시됐다. 반면 SSH 포트 2201~2204는 Tailscale IPv4 `100.100.136.37`에만 바인딩된다. Jupyter의 최종 외부 접근 가능 범위는 학교 방화벽·라우팅·호스트 방화벽·Jupyter 비밀번호를 합쳐 확인해야 한다. 이번 점검은 다른 네트워크에서 포트 접근 시험이나 관리자 권한의 방화벽 체인 조회를 하지 않았다.

**수정 묶음:** 실제 교내·외 접근 경로를 확인한 후 필요한 인터페이스에만 Jupyter 포트를 바인딩하도록 예약된 컨테이너 전환 때 조정한다. 실행 중 컨테이너의 포트 바인딩은 무중단으로 바꾸기 어렵기 때문에 GPU 파일과 세션 상태를 먼저 보존·검증해야 한다.

### 4. 운영 백업·복구 보증은 확인되지 않았다 — 중간

10월 17일 이전 GPU 컨테이너 4개와 그때 만든 이미지 4개는 남아 있다. 서버의 사용자 crontab과 systemd 타이머 조회에서는 CBGPU 자료·DB를 정기 백업하는 작업을 찾지 못했다. `cbgpu-materials`는 호스트 디렉터리를 bind mount하지만 별도 스냅샷/원격 백업·복구 시험은 확인하지 못했다. 다른 계정이나 외부 스토리지의 백업까지 조사한 것은 아니므로 **백업이 전혀 없다고 단정할 수 없다.**

**수정 묶음:** 관리자와 실제 백업 경로·주기·보관 기간을 확인하고, GPU 사용자 파일, 자료 공유 파일 및 Supabase DB의 복구 시험 계획을 기록한다. 기존 `*_backup_20261017`은 복구 검증 전 삭제하지 않는다.

### 5. 운영 가시성이 부족하다 — 중간

SSH 게이트웨이에는 인증·전달 및 양방향 종료 기록이 있으나 한 접속을 처음부터 끝까지 묶는 연결 ID가 없다. 자료 공유 컨테이너에는 최근 24시간 로그가 없고 Docker healthcheck가 없다. 네 GPU 컨테이너도 healthcheck가 없다. `cbgpu-daemon`의 warning 조회가 비어 있는 것은 기능별 성공 증거가 아니다. 최근 LAN 게이트웨이에는 시험 중 호스트 키 알고리즘 불일치와 미등록 키 거절 기록이 있었고, 별도의 사용자 장애인지 시험 결과인지는 이 로그만으로 판단할 수 없다.

**수정 묶음:** 게이트웨이 연결 ID와 단계별 종료 사유, 자료 공유·GPU·데몬의 readiness와 경보 기준을 만들고, 민감 정보가 로그에 남지 않도록 한다.

- `study-proxy`: 운영 함수의 기존 번들(버전 4)을 로컬 임시 파일로 보존했다. 새 코드의 번들 검사를 수행한 뒤 Supabase Edge Function 버전 5로 배포했다. 외부 HTTPS에서 비로그인 허용 경로 401, 금지 경로 403, OPTIONS 200을 확인했다. 승인 사용자에게 정상 자습 데이터가 조회되는지는 계정 세션이 없어 재시험하지 못했다.
- 알림 cron: `selfstudy-reminder-quarter-hour`가 `*/15 * * * *`로 활성화되어 있고 최근 5회 DB 실행 기록이 모두 `succeeded`임을 확인했다. 이는 cron의 HTTP 요청 실행 결과이며 실제 단말 수신까지 증명하지 않는다. Vault의 `cbgpu_service_role_key` 이름이 존재함만 확인했고 값은 읽거나 기록하지 않았다.
- 기상송 권한: 운영 `profiles`에 `guard_profile_privileged_columns` 트리거가 켜져 있고 함수 정의가 일반 사용자의 `is_wakeup_manager` 등 권한 변경을 거부함을 확인했다.
- 남은 운영 변경: 게이트웨이 연결 시간 로그는 현재 저장소에만 있고, 활성 SSH 연결을 끊는 재시작은 진행하지 않았다. Jupyter 바인딩 변경도 다음 안전한 GPU 교체 시 반영된다. Vercel 배포 커밋과 별도 백업 체계는 아직 확인되지 않았다.
- Supabase 개인 접근 토큰이 대화에 노출됐다. 필요한 운영 확인이 끝난 뒤 토큰을 폐기하고 새 토큰을 발급해야 한다. 토큰 값은 저장소나 문서에 기록하지 않았다.
