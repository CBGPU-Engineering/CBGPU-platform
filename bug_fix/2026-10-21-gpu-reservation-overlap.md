# GPU 예약 중복 신청 및 사용 중단 실패

## 운영 DB 확인 (2026-10-21)

- 확정 예약끼리 겹친 쌍: **0**.
- 대기 신청과 확정 예약이 겹친 쌍: **1**. GPU 2의 대기 신청이며, 기존 확정 예약과 기간이 겹친다. 대기 신청은 사용자 요청대로 그대로 유지했다.
- `reservations_approved_no_overlap` 및 `reservations_valid_window` 제약은 운영 DB에서 유효 상태로 확인했다.

## 원인

1. 로그인 사용자의 `reservations` SELECT 정책은 본인 행만 반환했다. 웹과 앱은 같은 테이블에서 **모든 사용자의 확정 예약**을 읽은 결과로 빈 시간을 판단했다. 따라서 다른 사람의 예약은 화면에서 빠졌다.
2. 일반 사용자에게 본인 예약의 `end_time`을 바꿀 UPDATE 정책이 없었다. 웹과 앱의 “사용 중단” 요청은 오류 없이 0행을 바꿀 수 있었고, 두 화면은 변경 행 수를 확인하지 않아 성공 메시지를 띄웠다.
3. 기존 INSERT 정책 중 하나가 `WITH CHECK true`여서 인증 사용자가 다른 계정의 예약이나 `approved` 상태를 직접 INSERT할 수 있었다.
4. DB에 시간 충돌 제약이 없었다. 관리자 화면의 클라이언트 검사만으로는 최신 상태·동시 승인을 보장하지 못했다.
5. 관리자 화면은 승인 시 GPU 비밀번호를 먼저 바꾸고 예약 상태를 나중에 바꿨다. 두 번째 작업이 실패하면 비밀번호만 바뀔 수 있었다.

## 적용한 수정

- [`guard_gpu_reservation_overlaps.sql`](../Migrations/guard_gpu_reservation_overlaps.sql): 본인 명의의 대기 신청만 허용하는 INSERT 정책, 진행 중인 본인 예약의 사용 중단만 허용하는 UPDATE 정책·트리거, 같은 GPU의 대기/확정 신청 충돌 방지, 확정 예약끼리의 겹침 금지 제약. 2026-10-21 운영 DB 적용 완료.
- [`gpu_reservation_schedule.sql`](../Migrations/gpu_reservation_schedule.sql): 승인된 예약용 일정 조회와 대기까지 포함한 신청용 일정 조회 함수를 분리했다. 둘 다 예약 시간과 GPU 번호·예약 ID만 반환한다. 운영 DB 적용 완료. 익명 권한 API 호출에서 GPU 2의 같은 기간에 확정 1건, 대기 포함 2건이 반환됨을 확인했다.
- [`approve_gpu_reservation.sql`](../Migrations/approve_gpu_reservation.sql): 관리자 승인과 GPU 비밀번호 갱신을 단일 트랜잭션으로 묶었다. 운영 DB 적용 완료.
- 웹·앱 예약 화면은 일정 함수를 사용하고, 충돌 시 서버 오류를 명확하게 보여 준다. 사용 중단 후에는 실제 변경 행이 있는지 확인한다. 관리자 화면은 기존 충돌 대기 신청에 `확정 예약과 시간 겹침`을 표시하고 승인을 비활성화한다.

## 검증 및 배포 상태

- 운영 DB에서 확정 예약 중복 0쌍, 대기/확정 중복 1쌍을 읽기 전용으로 재확인했다. 기존 대기 신청을 삭제하거나 승인하지 않았다.
- 익명 권한의 승인 함수 호출은 `42501`로 거부됨을 확인했다. 실제 예약 ID는 사용하지 않았다.
- 웹 `npx tsc --noEmit` 통과. Next 전체 빌드는 이 실행 환경에서 Turbopack의 로컬 포트 생성이 `Operation not permitted`로 실패했다. Flutter SDK가 없어 앱 정적 분석은 실행하지 못했다.
- 운영 중인 사용자 예약을 잠시 수정하고 롤백하는 실사용 검증은 자동 승인 검토가 활성 행의 잠금·트리거 부작용 위험 때문에 거부했다. 해당 검증은 수행하지 않았고 운영 행도 수정되지 않았다.
- DB 보호는 즉시 적용됐다. 화면 수정은 웹 배포 및 앱 배포 후 반영된다. 기존 운영 웹·앱은 아직 기존 조회/승인 흐름을 쓸 수 있지만, DB는 새 충돌과 무권한 INSERT를 거부한다.
- 기존 `anon` 전체 예약 SELECT 정책에는 개인 정보 노출 위험이 남아 있다. 새 일정 함수만 쓰는 웹 버전의 배포 확인 후 해당 정책을 제거해야 한다. 먼저 제거하면 기존 배포 화면의 달력 조회가 끊긴다.
