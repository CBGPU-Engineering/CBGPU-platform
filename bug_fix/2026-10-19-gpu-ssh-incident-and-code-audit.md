# GPU SSH 접속 장애 및 코드 점검 — 2026-10-19

## 확인된 사실

- 교내 사용자 PC의 DNS가 `cbshoj.taild105d1.ts.net`을 `127.0.0.1`로 응답했다는 보고를 받았다. 이 DNS 결과는 해당 PC에서 관찰한 것으로, 서버에서 독립적으로 재현하지 않았다.
- 이 PC가 공개 Funnel 릴레이 IP로 우회한 뒤에는 TLS 인증서와 게이트웨이 SSH 호스트 키를 확인하고 게이트웨이 인증에 성공했다. GPU 1~3의 예약 거절도 정상 동작했다.
- 서버 로그에서 GPU 4 접속은 2026-10-19 11:13:53 UTC에 게이트웨이 인증, 11:13:55에 포트 전달 시작, 11:13:58에 전달 종료로 기록됐다. 11:15에도 같은 패턴이 반복됐다.
- 운영 DB의 현재 GPU 4 예약 계정 공개키와 컨테이너 `/root/.ssh/authorized_keys`의 키가 일치한다. 컨테이너 SSH 데몬은 실행 중이며, **서버 내부**에서 `100.100.136.37:2204`에 접속하면 SSH 배너가 즉시 돌아온다.
- 사용자가 일반 VPN을 켠 뒤에도 **같은 공개 게이트웨이**를 사용했다. 서버에는 11:16:00 UTC부터 GPU 4 전달 연결이 유지되는 모습이 기록됐다. 사용자 PC에 Tailscale이 설치됐다는 근거는 없다.
- 독립 TCP 검사 서비스의 해외 노드 7곳에서는 공개 `10000`번 포트 연결에 성공했다. 이는 모든 학교망의 접속 성공을 보장하지 않는다.

## 원인 판단과 남은 확인

교내 PC의 DNS 응답이 루프백으로 바뀐 것은 기본 공개 주소 접속이 실패하는 직접 원인이다. 공개 릴레이 IP를 지정한 뒤에도 VPN이 꺼진 상태에서 GPU 4 전달이 짧게 끝나는 이유는 아직 확정되지 않았다. 교내망의 포트·트래픽 정책, 클라이언트 SSH 설정·호스트 키 검증, 게이트웨이의 조기 종료를 구분해야 한다. 운영 게이트웨이에는 11:10 UTC부터 인증·전달 단계 로그를 추가했다. 이후의 클라이언트 시도 시각과 서버 로그를 대조한다.

게이트웨이 코드에서 양방향 복사 중 한쪽이 EOF를 보내면 양쪽 소켓을 즉시 닫는 결함을 확인했다. 한쪽 쓰기만 종료하고 반대쪽의 남은 응답을 전달하도록 수정했으며, 반쪽 종료 후 응답이 도착하는 회귀 테스트를 추가했다. 활성 전달 세션이 없음을 확인한 뒤 11:22:48 UTC에 공개 게이트웨이에 배포했다. 그 뒤 서버 측 시험에서 Supabase 예약 조회가 8초 제한에 걸려 인증이 거부된 기록이 나왔다. 직후 조회는 빠르게 성공했다. 따라서 일시적인 조회 지연도 별개의 접속 실패 원인이다. 각 조회를 최대 세 번, 요청당 최대 6초로 제한해 다시 시도하도록 수정했다. 전체 인증 제한은 22초이며, 계속 실패하면 기존처럼 접근을 거부한다. 이 재시도 버전은 LAN 게이트웨이에 적용했고 공개 게이트웨이에는 아직 적용하지 않았다.

학교 LAN 전용 게이트웨이는 사용자의 명시적 설치 승인 후 11:27:51 UTC에 `10.138.23.12:22220`에서 활성화했다. 같은 예약·공개키 검사와 SSH 호스트 키를 사용하며 기존 공개 서비스를 변경하지 않았다. 서버에서 리스너와 SSH 호스트 키 지문을 확인했고 미등록 공개키 접속이 거부됐다.

11:33:47 UTC에는 교내 Wi-Fi 노트북 `10.138.25.124`에서 `10.138.23.12`로 가는 경로가 물리 무선 인터페이스임을 확인했다. 새 임시 키와 빈 SSH 설정, 별도 known_hosts 파일을 사용하고 SSH 에이전트·ProxyCommand·ProxyJump를 끈 상태에서 LAN 게이트웨이의 TCP 연결과 호스트 키 지문 확인에 성공했다. 미등록 키는 예상대로 거부됐다. 따라서 **이 교내 Wi-Fi 구간의 포트 접근**은 검증됐다. 이 시험은 등록된 예약자 키로 GPU 컨테이너에 로그인하는 종단 간 시험은 아니다. 다른 교내 PC·망 구간까지 보장하지 않는다.

## 다음 확인 순서

1. 실제 예약자의 교내 PC에서 VPN을 끈 상태로 LAN 경로 `ssh cbgpu-gpu4-school`을 실행해 예약 GPU 로그인을 확인한다. 미예약 GPU 거절도 확인한다. 다른 교내 구간에서 방화벽에 막히면 서버 관리자 권한으로 정책을 확인한다.
2. 공개 게이트웨이의 활성 세션이 없는 시점에 조회 재시도 버전을 배포하고, 예약자 접속과 예약 종료 시 세션 차단을 재검증한다.
3. 웹 린트 오류를 영향 범위별로 줄이고 CI에 TypeScript·빌드·린트·Go/Python 테스트를 추가한다. 앱 분석은 Flutter SDK가 있는 환경에서 별도로 실행한다.
