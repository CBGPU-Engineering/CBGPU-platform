# 같은 학년도 학번 중복 계정

- 조사일: 2026-10-16
- 기준: 같은 학년도(한국 시간 3월~다음 해 2월)에 같은 4자리 학번을 가진 프로필
- 상태: 현황 조사 완료, 신규 중복 차단 SQL 운영 DB 적용 확인, 기존 중복 정리 대기

## 현황

운영 데이터를 읽기 전용으로 조사했다. `profiles` 142개, Auth 사용자 150개였다.
같은 2026학년도 학번을 가진 그룹은 14개이고, 각 그룹에 프로필 2개씩 총
28개 계정이 있다. 12개 그룹은 두 프로필의 이름이 같고, 2개 그룹은 이름이
다르다. 이름 일치만으로 동일인 여부를 확정할 수 없다. 중복 그룹 중 2개는
GPU 예약 이력이 있으므로 계정 병합이나 삭제를 자동 수행하지 않는다.

Auth 사용자 8개는 프로필이 없었고, 학번이 없는 프로필도 8개 있었다.
프로필이 없는 사용자는 가입 시 프로필 생성에 실패한 것인지 별도 조사가
필요하다. 프로필의 학번과 Auth 메타데이터의 학번이 다른 사례도 1개였다.
이 집계에는 이메일, 이름, 사용자 UUID를 기록하지 않았다.

## 원인

가입 화면은 학번 형식만 확인한다. `auth.users` 생성 트리거가 학번을
`profiles`로 복사하고, 프로필 화면에서는 학번을 변경할 수 있다. 같은
학번의 다른 계정을 막는 DB 제약이나 검사 기능이 없었다. 이메일이 달라도
같은 학번으로 가입할 수 있었다.

## 차단 설계

`FrontEnd/cbgpu/supabase_student_id_duplicate_guard.sql`을 적용하면 기존
프로필의 가입일에서 학년도를 채우고, 새 학번 등록 시 해당 학년도에 같은
학번이 이미 있는지 검사한다. 동시 가입 요청은 학번별 advisory lock으로
직렬화한다. 기존 14개 중복 그룹은 유지하며, 새 중복 등록만 거부한다.
계정 삭제 과정에서 서비스 역할이 학번을 비우는 동작은 유지한다.

학년도는 한국 시간 기준 3월 1일부터 다음 해 2월 말까지다. 다음 학년도에
학번을 재사용할 수 있다. 가입 화면에는 한 학년도에 학번당 한 계정이라는
규칙과 기존 계정 복구 안내를 표시한다.

## 운영 적용 및 남은 작업

1. Supabase SQL Editor에서 `supabase_student_id_duplicate_guard.sql` 실행.
2. 새 테스트 계정으로 이미 쓰는 학번 가입은 거부되고, 사용하지 않는 학번
   가입과 기존 사용자 프로필 수정은 성공하는지 확인.
3. 14개 중복 그룹은 계정 소유자와 예약 이력을 확인한 뒤 수동 정리.
   현재 자료만으로 어떤 계정을 남길지 자동 결정할 수 없다.
4. 중복 정리 후 `(student_id_school_year, btrim(student_id))` 고유 인덱스를
   추가해 DB 고유성까지 강제. 현재는 기존 중복 때문에 바로 만들 수 없다.
5. 프로필이 없는 Auth 사용자 8개의 가입 경로와 복구 방안을 별도 조사.

## 2026-10-17 적용 확인

사용자가 SQL Editor에서 `supabase_student_id_duplicate_guard.sql`을 실행했다.
이후 운영 DB를 읽기 전용으로 조회해 `student_id_school_year` 컬럼과
`cbgpu_school_year` 함수가 존재함을 확인했다. 학번이 있는 프로필 135개는
모두 학년도 값이 채워졌고, 함수는 2026-10-17에 대해 2026학년도를
반환했다. 운영 DB의 재집계는 프로필 143개, 2026학년도 중복 15그룹
(30개 프로필)이다. 2026-10-16의 14그룹은 당시 조사 결과이며,
두 수치의 차이를 특정 계정의 신규 가입으로 단정하지 않는다.

트리거가 실제 가입 요청을 거부하는 동작 테스트와 기존 중복 계정 정리는
아직 완료되지 않았다. SQL 적용 전 작성한 위 운영 적용 목록의 1번은
완료됐고, 2~5번은 남아 있다.
